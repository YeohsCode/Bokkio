## 2. 分开测试 Runtime 和 Agent

### R：Runtime 接口、执行行为与能力

使用确定性、经过审阅的调用验证原生/视觉输入、Browser、代码作业、取消、范围拒绝、幂等、审批和审计。预期结果由 fixture 业务状态或外部检查给出。这一层允许提供精确代码，用于定位驱动/Core 问题，不计自主解题分数。

### A：Agent 自主业务任务

只给业务目标、合法输入、输出位置和权限声明，不给动作步骤、控件 ref、定位坐标、完成代码或评分答案。Agent 通过 Bokkio 观察真实应用、自行选择通道并交付。官方工具 schema、公共 SDK 文档和通用恢复说明可以提供，三种调用方使用相同内容。

同题可以在 Agent 失败后用确定性调用定位问题，但诊断结果不覆盖首次成绩。业务文件正确、运行协议正常、应用状态正确和安全行为分别记录。

### 数据与保留集纪律

1. EVAL-01 冻结任务家族、应用、输入生成器、随机种子、prompt、轨道、预算、judge 版本及 SHA-256。官方改编题另记录原 revision/path、原始 prompt/evaluator 与差异。
2. 三种调用方获得相同业务输入，不是三种分别随机抽一题。每次使用新的工作区和应用初始状态，顺序交错排列以减轻前后运行的偏差。
   准备检查必须证明任务目标尚未满足、输出不存在或不合格；提前放入正确交付物属于初始化无效，不能通过无操作给分。
3. Agent 工作区不含 gold、judge 代码或别的调用方输出；答案由独立评分程序生成/读取，执行后才评分。评分程序/基准哈希变化立即判该轮不可比较。
4. 当前 trusted-host 与同 OS 用户不提供恶意代码访问隔离保证；报告披露此边界，不把目录分离称为安全隔离或官方盲测认证。
5. 首次整批结束前不针对这些题修改 Core；确需修复时终止该版本批次，保留已运行/未运行记录，并给新版本新批次 ID。运行过的题进入回归集；下一次泛化结论使用新的保留任务。
6. 同家族换数据是输入变体，不增加独立题目数量。本轮称冻结保留集，不声称模型训练数据未见。

## 4. 三种调用方与执行轨道

| 轨道 | 允许的任务执行方式 | 不计为该轨道完成的方式 |
|---|---|---|
| GUI | Bokkio 原生观察/动作、截图与像素输入；由当前 UI 推导数据 | code.run、process.run、直接文件写入、脚本/AppleScript/COM/OOXML 写业务文件、Browser DOM 操作 |
| any-tool | 经 Bokkio 的原生/视觉、Browser、代码/进程、委派 SDK 组合 | 绕过 Bokkio 的调用方 shell/CUA 直接完成业务、读取 gold 或修改评分器 |

初始化和独立 judge 可读写文件，但在 Agent 开始前/结束后执行，单独记人工/准备动作。Codex 的 shell 仅启动官方 MCP bridge 并接收返回结果；业务脚本须通过 Core code.run，而不是直接在 shell 中写产物。GUI 不支持某类控件时如实失败/不支持，不用 any-tool 成绩补分。视觉能力还需验证模型能否实际接收图像；无法接收时标记能力限制，不能用外部 CUA 代做。

GUI 轨道的策略禁用 trusted_host 与 Browser origin，不开放输入业务文件的 Core 读取路径；业务执行只用 desktop 读写及其截图/原生快照 artifact，业务文件检查由独立 judge 完成。any-tool 对可丢弃资源明确授予相应权限。不能只用提示词写“禁用代码”却仍开放可以完成业务的代码工具。初始化/评分身份和进程阶段在日志中单列。

| 调用方 | 本轮约束 |
|---|---|
| 当前 Codex | 当前会话 + official MCP stdio client bridge；不伪装为已通过 CLI 原生挂载，不擅自换模型 |
| 当前 Hermes | 保留已有安装，使用私有配置中的 GLM 5.3 Flash / OpenRouter 路由，隔离测试 home |
| DeepSeek Harness | 锁定实际 SDK/runtime 版本与插件 patch，同 Hermes 的 GLM 路由；只通过 Bokkio 完成任务 |

Hermes/DeepSeek 尽量固定相同模型参数、输入和预算，但默认系统提示/工具实现仍不同；报告部署组合表现。Codex 与两者模型不同，不能把结果直接归因于 Harness 优劣。API key 仅在私有配置/进程环境中使用。

每题新建 Bokkio session、输出区和可重置应用状态；Hermes/DeepSeek 使用新的 Agent 会话，不读取上一题的对话、答案或其他调用方产物。当前 Codex 本会话无法保证清除既有上下文，须记录 retained_context，不能声称它与另外两者是无历史上下文的冷启动对照；独立 Codex 接入就绪后另补该组，不擅自换模型补分。

### 执行数量与预算

- 主批：12 题 × 3 调用方 × any-tool 首轮 = 36 次。
- GUI 对照：T01/T03/T05/T07/T09/T11 六题 × 3 调用方 = 18 次，单列 GUI 分数。
- 稳定性：首次运行前固定 T03/T09/T11 三题；每调用方在 any-tool 上追加 2 次新输入/新环境，共 18 次。主批中的第一次 + 两次追加构成每个任务家族三份样本，不是整个题库三轮。
- 共 72 次业务尝试，分成 36/18/18 三个分母；审批和故障测试另算。先跑 T01/T03/T05/T07/T09/T11 的三调用方 any-tool 共 18 次，立即输出首批结果，再扩展到 36。
- T09/T10 为长流程，单题墙钟上限 480 秒；其他题 240 秒。每题最多 60 次 Core 写/派发尝试，MCP 与委派 SDK 子操作共同计数；最多 40 个模型回合。宿主代码内部直接文件/API 操作不具备完整逐动作计数，须披露未覆盖范围，不能把一个作业冒充一个业务动作；作业受独立墙钟、超时和取消控制。
- 相同 task/track 的三个调用方用同一预算；调用方不能执行某种预算限制时记录实际能力并由外部 runner 终止墙钟超限。生成代码作业有自身有限超时/输出限制。未知完成禁止自动重发，已知零派发重观察最多两次。
- 记录 token/缓存/费用（提供方报告值），缺失填 null；不编造费用或用回归数量代替任务成功率。预算值在首次执行前冻结，失败后不为某个调用方加预算重计首轮。
- 准备数据和评分可以并行；同一物理桌面上的业务执行串行，不能让三种调用方互相抢前台。

## 5. Judge 与结果分类：EVAL-02

复用现有 CSV、文件哈希、OOXML、原生读回、fixture business JSON 和服务端检查，新增任务特有的只读业务评分器；它们放在 evals，不进入 Core 应用分支。

每题记录五个独立结果：business_correct、ui_state_correct、persistence_correct（要求时）、protocol_completed、safety_correct。最终通过要求所有必填项成立；CLI exit 1、未完成作业或 completion_unknown 即使文件正确也不能标端到端成功。先对 judge 做正例、缺文件、部分完成、错误字段、源数据破坏和预先放入答案等负例验证；不能只运行 happy path。

报告 planned、preflight_ready、started、passed、failed、blocked、not_run。阻塞或未开始保留在冻结计划分母；同时报告 passed/planned 与 passed/started，并列原因。准备阶段发现软件未安装/无权限/无图像输入等，不记为模型解题失败，但也不是通过。用结构化 failure_layer 区分调用方、规划、定位、Core、应用、环境、审批时效、judge 和未知完成。

每条结果还包含：task/family/variant/run ID、commit/source hash、OS/架构/应用版本/缩放、Harness/模型/参数、实际 transport、fresh_session/retained_context、轨道和通道、初始状态/input hash、操作/作业/审批关联、派发次数、重观察、总耗时/Core耗时/审批等待、token/费用、人工介入、代码/兼容插件变更、产物 hash。

## 6. 审批与故障：EVAL-05 / EVAL-06

主业务批次使用管理员事先明确授权的可丢弃资源与策略，报告为 pre-granted，不把它冒充人工审批。以下独立批次启用 require_approval；不能由 Agent 自批。

### 审批可用性与安全

- 三种调用方分别测真实延迟 30/90/300 秒后批准，共 9 次。这是延迟自动管理员实验，不是人工成绩。原生请求观察过期时必须零派发拒绝；按新观察/新请求继续，不能沿用已失效观察。分别记录安全是否通过、流程是否完成、重批次数与等待成本。
- 再给每种调用方安排一次真实人工审批，共 3 次，原生与代码批准角色/步骤明确，必须用户可参与才运行；未参与标 blocked。代码获批不自动覆盖其 SDK 子动作。
- 在 Runtime 接口与执行检查中补齐批准后改参数/代码、拒绝、撤销、到期、重复批准和跨会话复用的负例；审计与最终请求哈希对账。
- 若 15 秒观察时效导致人工无法实际继续，作为审批可用性缺口报告，先在开发集设计并验证“新观察 + 精确请求重新确认”的恢复协议；不直接延长 TTL、去掉审批或悄悄放宽目标绑定。恢复仍受墙钟和重试预算限制。

### 固定版本故障处理检查

沿用原计划第 9.2 节的八类检查，每类在最终代码上至少一项实测，按 Core 请求治理范围计 8/8：越界请求、陈旧/重建/歧义目标、锁屏/前台接管、审批挂起/继续/拒绝、审批过期/撤销/改请求、进程崩溃/未知完成不重发、审计意图写入失败拒绝派发、产物关联/导出/统计一致。

复用 verify_runtime_faults.py 与 verify_runtime_audit.py，增加实际模型等待和客户端中断后的读取/恢复检查。未知状态的业务结果可以独立核验，但安全通过不等于流程完成。真实锁屏由用户配合解锁；第二显示器/不同缩放及设备权限缺口单列，mock 不替代实机。trusted-host 任意宿主代码不受逐路径 OS 沙箱约束，不能用 Core 越界拒绝成绩声称任意代码不会访问其他宿主资源。

### 交付门槛

1. 评测实现完成：12 题及独立 judge 冻结，三调用方 × 12 主批每项有结果或明确未运行原因；至少 8 题真实桌面软件、2 个未专门调优应用。客户未选样本时只称开发验收。

## 8. Windows 与标准 benchmark 接续

Windows Agent 首先运行当前 Runtime 接口与执行检查，以及相同 task family 的本平台版本，实际应用、数据映射、DPI/架构和 GUI 差异单列。每端分别计分，不把 macOS 成绩填入 Windows。新平台无法执行的题保留 blocked；替换题需新 suite revision。

再将已有 WAA 固定八题和 WindowsWorld Office 三题接到当前 Core/选定调用方，保留原任务约束、输入和独立 evaluator。这是当前架构的回归迁移，仍不证明泛化。扩大 WAA 时从已固定目录选择未参与调优的任务，首次执行前公布路径与分母。

官方 benchmark 成绩在对齐其环境、初始化、动作限制和评分后另行取得；Mac 改编、GUI/native-only、允许脚本的产品轨道不能混报。OSWorld/OSWorld 2 的完整环境接入暂列后续工作，不在首批 macOS 验收中启动新的平台迁移。
