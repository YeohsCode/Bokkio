# Bokkio 桌面 UX、Shortcuts 录制回放与实机验证计划

> 实施更新（2026-10-15）：当前产品为 Electron 桌面应用，四入口已接通本机 Runtime；本轮进度和实测见文末与[证据报告](evidence/2026-10-15-desktop-studio/README.md)。下文保留 r3 设计与验收目标。
日期：2026-10-14。版本：r3。评审源码：`89f1564`。当前任务只更新设计、计划和交互原型，未实施功能。本计划取代 `SHORTCUTS-WORKFLOW-PLAN.md` 中纯 Web Studio 和仅支持原生控件的首版方案。

## 1. 唯一推荐及代价

采用 **Electron 桌面宿主 + React/TypeScript 界面 + 现有 Python Runtime + macOS Swift / Windows Python 原生捕获器**。禁止 Java；不引入 JVM、Repeat 或依赖 Java 的组件。TypeScript/JavaScript 不属于 Java。

应用安装后从 Dock/开始菜单启动，自动管理本机 Runtime 和捕获进程。主窗口、录制浮条、目标选取覆盖层、托盘及全局停止键由桌面宿主管理。用户不需要启动 Terminal、打开浏览器或配置 localhost 端口。

Electron 的屏幕采集与全局快捷键 API 可支撑两平台桌面交互；键鼠全过程仍由原生 Hook/AX/UIA 处理。Web 页面只负责绘制界面。普通网页既不能读取系统 UIA/AX，也不能监听任意应用的全局键鼠事件，之前将“已有 Web 页面”当成完整 UX 方案不成立。

选择 Electron 的收益是共用 Chromium、成熟的窗口/录屏/自动化测试基础和前端交互；代价是更大的安装包及内存、Node/Chromium 更新，以及 Python sidecar 的分平台打包。此次接受这些成本，先完成统一桌面产品，不重写既有驱动。

现有 Studio 的业务 API/版本库/运行器复用，页面逐步迁到统一 React 应用。Electron preload 暴露具名 IPC 接口；main 启动 sidecar 并转发事件，内部可先复用随机令牌 localhost API。网络页面和模型输出不获得 Node/任意 IPC 调用能力。后续可替换内部传输，产品不暴露端口。

## 2. 整体 UX 与功能归属

同一桌面应用、同一工作区、同一任务/流程 ID。四个入口与共用运行详情相互跳转，不建设四套孤立界面。

| 入口 | 功能 | 和其他入口的关系 |
|---|---|---|
| 设置 | 模型服务地址/模型/API Key、连接测试、Harness、工作目录、录制画面来源、停止键、本机系统授权状态、执行模式 | 保存后对话和 Shortcuts 共用；API Key 进入系统凭据存储，不进入 Workflow/聊天日志 |
| 对话与任务 | 历史会话、任务输入、附件、流式回复、计划/工具执行进度、暂停/停止、结果文件；引用 Shortcut、填参数并执行；从成功任务保存流程 | 默认接入已有 DeepSeek Harness 路径，工具动作走当前 Runtime；任务卡直接打开运行详情或 Shortcut 编辑器 |
| 录制与回放 | 应用/显示器选择、开始/暂停/停止、桌面浮条、步骤计数、画面预览、事件时间线、缺口提示；前台回放、单步调试、进度和结果 | 录完自动打开 Shortcut 草稿；回放结果回到流程历史或发起任务的对话 |
| Shortcuts 维护 | 搜索/分组、名称/说明、版本、参数、应用绑定；步骤列表/属性编辑、复制/删除/重排、撤销/重做、等待/验证表单、录制片段、目标重新选择、导入导出、运行历史 | 保存新版本；编辑不影响正在运行的冻结版本；可重新录制选中片段替换步骤 |

配置和聊天界面当前尚未实现。现有源码只有 Workflow Studio 页面、模型私有配置文件和 CLI/Harness 入口。新增聊天界面复用 Harness，不另造第三套 Agent loop；现有旧 DesktopAgent 直接调用 backend 的路径不能原封不动接成新的主界面执行路径。

### 关键用户旅程

1. 首次启动：选择工作目录，配置并测试模型。无模型配置仍可录制/回放。系统授权在首次真正需要该能力时引导。
2. 对话执行：输入任务 → 显示执行中的步骤 → 查看结果；复用已保存流程时展示参数表单，点击运行直接执行。
3. 人工录制：选择目标应用/画面来源 → 倒计时 → 主窗口收起/回到目标应用 → 浮条显示录制状态 → 停止 → 自动载入步骤与片段 → 编辑/参数化/保存。
4. 日常回放：选 Shortcut → 填参数 → 运行 → 桌面浮条显示当前步骤和停止键 → 查看结果或进入失败步骤。
5. 维护：选失败步骤 → 查看原录制片段与当前目标 → 重新选控件、改参数/等待/检查，或重录该片段 → 保存新版本 → 用明确初始状态重测。

r3 规划时的交互设计为会话内 `bokkio-studio-workbench.html`，取代 r2 的 `bokkio-desktop-ux.html`。上一版只是页面入口和表单，没有把参考项目的编辑/调试操作转成完整工作台。

### 参考项目如何落实到 UX（r3）

以 CrossMacro 的自动化编辑器为骨架：左侧流程库，中间录制画面与步骤表，右侧选中步骤属性，底部日志/变量/运行记录。保持一套设计，不提供竞争方案。

| 交互来源 | 本项目具体采用 | 设计预览中可以操作 |
|---|---|---|
| CrossMacro 步骤列表/属性编辑 | 流程选择、目标/内容/验证属性页、时间线与目标高亮 | 选步骤、改目标/动作/内容、联动对应画面 |
| CrossMacro 批量编辑 | 多选、复制/删除、重排、停用、撤销/重做、插入动作 | 改变实际草稿；撤销恢复；拖动或按钮调整顺序 |
| CrossMacro 录制/回放控制 | 鼠标/键盘/画面来源开关，速度/次数，独立录制页与桌面浮条 | 捕获演示事件，暂停，停止后载入草稿；回放演示读取速度和次数 |
| Ui.Vision 调试 | 行级断点、单步、继续/停止，日志和变量面板 | 在发送步骤前暂停，检查参数后继续；执行日志和步骤状态联动 |
| KeymouseGo 快捷操作 | 录制/暂停/停止快捷控制就近可见，设置中配置按键 | 设置入口、浮条状态和冲突信息的位置明确；全局键注册属于后续系统实现 |

隐藏鼠标移动只改变呈现，不删除、停用或改变回放；多选和主选中步骤区分。录制画面、步骤、属性和调试面板共享选中步骤；切换流程同时切换草稿和画面。日常运行从对话或流程库调用，完整工作台负责维护和调试。

原型演示编辑与调试状态，不执行系统动作。后续产品实现必须保留这些行为；不能以能打开四页或按钮能弹提示作为 UX 完成标准。

## 3. 录制：操作数据与画面同时采集

### 3.1 录制产物

一次录制生成：

- 结构化输入事件：相对时间、顺序、窗口切换、点击/双击/右键、键盘组合、文本提交、滚动、拖拽；每项带定位和输入传输信息。
- 语义目标：应用安装身份、窗口/文档上下文、role/name、AXIdentifier/AutomationId、父级路径、范围和原生可执行能力。
- 辅助定位：目标范围内的点击比例、局部图像锚点/文字、显示器和缩放变换。画布没有语义树时仍能录制成视觉/输入步骤。
- 画面录像与片段索引：视频用于人工审阅，点击步骤可定位到对应片段；不从视频猜测已发生的键盘/点击事件。
- 可执行 Workflow：文本归并、手势归并、等待/验证、参数、版本、原始事件/片段关联。

首版提供完整“操作录制 + 可回看的画面”。默认保存画面，可在设置关闭画面而继续录操作；不录音频。不能把视频回看和自动化回放混为一谈。

### 3.2 输入捕获

macOS：复用并扩展 Swift CGEventTap，配合 AXUIElementCopyElementAtPosition、焦点/值观察和窗口事件。加入右键、拖拽起止与轨迹、滚动、组合键；文本使用提交后的内容而非拼出输入法中间态。

Windows：Python 捕获进程通过 ctypes 调用 WH_MOUSE_LL/WH_KEYBOARD_LL；UIA 使用 ElementFromPoint/BuildCache、焦点、ValuePattern/TextPattern 与可用事件。捕获进程拥有专用 COM 线程；回调只写最小有序事件，UIA 查询/文本读回在独立队列处理，COM 对象不跨线程传递。

点击在 mouseDown 保存位置、窗口、时间和近时刻目标缓存，mouseUp 完成动作归并。菜单/弹窗可能在点击后立即消失，不能等到点击完成才用整窗快照找目标。对短暂目标使用命中缓存/属性缓存；仍未捕获身份时保留输入和局部画面进入视觉步骤，不静默删除。

同名控件在具体窗口/父级上下文消歧，AutomationId 不作为全局唯一标识。运行时 ref/PID/HWND 不作为应用重启后的持久身份。单调时钟和录制会话序号用于排序；视频和 sidecar 时钟通过 IPC 校准，记录漂移与丢帧。

输入法、粘贴、快捷键必须区分：文本内容可读回时固化成文本提交；复制/粘贴/保存等组合键保留命令行为，不能都变成最终字段值。不可读编辑区保留实际输入轨迹并在审阅时补足文本内容/提交方式，允许用户修正；不能因此禁止录制整个应用。

### 3.3 屏幕视频与持久化

Electron main 的 desktopCapturer + session display-media handler 选择画面源，专用 capture renderer 通过 MediaRecorder 生成视频。捕获窗口独立于主 UI 生命周期；主窗口最小化/切页不停止录制。后台节流关闭，录制浮条不取得键盘焦点。

起始设置：所选显示器、15 fps、保留画面可读性、不录音频；多个显示器分别保存画面段并记录映射。跨显示器或缩放变化更新坐标变换，不能把 DIP 直接当物理像素。

视频分块落盘、有背压，定期封段；停止时 flush、关闭流并核对片段。磁盘满、capture renderer 崩溃、原生监听中断要让浮条立即显示真实状态，保留已完整封段和已捕获步骤。恢复最后未封段不能靠假设 WebM timeslice 每块都独立可播放，须实际验证恢复。

密码原生控件不读取明文；录像中的敏感区域需要遮挡或暂停采集，普通聊天画面仍可能被保存，录制范围和“暂停”必须随手可见。录制自己的控制界面、停止键、sidecar 注入事件都需排除，避免把回放重新录进去。

### 3.4 事件编译为步骤

连续文字编辑归并为文本步骤，组合键保留命令，连续滚动归并到容器，拖拽包含起点/终点定位和必要轨迹。每个步骤保存目标定位、原行为、执行传输、等待/验证和视频时间段。

步骤分为 native、anchored-input、visual-input、browser 和 code。新增输入步骤与录制元数据采用明确的新 Workflow schema，提供 v1 导入转换；不把未声明字段塞进当前严格 v1 文档。截图/视频与原始事件独立存储，通过 artifact ID 关联，不塞进 JSON base64。

原生、视觉和输入步骤均是产品正式能力；不能把所有 AX/UIA 未暴露控件一概丢给用户手写脚本。

## 4. 回放：重新定位后重现操作，并检查结果

默认前台智能回放，支持真实键鼠行为；后台原生回放作为单独执行模式。

1. 冻结版本和参数，绑定应用/文档，恢复用户配置的初始窗口或文件。应用安装身份和文档路径分别处理；启动应用不能当成打开了业务文件。
2. 按步骤等待窗口/控件/图像/文字/文件条件，不机械照搬录制耗时。
3. 重新定位目标：AX/UIA 语义定位、DOM 定位或局部图像/OCR 定位；相对位置作为已识别窗口/锚点内的定位辅助，不裸放旧屏幕坐标。
4. 执行该步骤记录的行为：原生方法在应用行为等价时使用；否则对新目标位置派发鼠标、Unicode 文本、组合键、滚动或拖拽。快捷键、拖拽和复杂编辑不能假装用 set_value 代替。
5. 检查 UI 状态及文件/业务产物。没有强检查时显示“操作已执行，结果未验证”，不把 present=true 写成业务成功。
6. 保存操作回执/检查点并推进。定位/等待失败可重新观察，已经执行但结果不明的动作先查结果，不能直接再发一遍。

当前 Runtime 还没有完整桌面组合键、右键、拖拽接口，desktop.pixel 只提供 click/type；本计划要正式扩展统一输入工具与 WorkflowRunner。新输入通过 Runtime 获取回执，不用 UI 内部 pyautogui/pynput 偷跑第二条执行路线。

当前整张截图变化可能受光标/动画干扰。锚定输入应核对目标窗口、焦点、几何、可见/遮挡状态和局部锚点；无关区域动画不能一律导致失败。目标移动/遮挡则重新定位。此项需要真实闪烁光标、菜单和动画界面测试。

单步/断点用于调试；“从选中步骤继续”须核对该步骤的前置状态。重录片段或重新绑定是编辑功能，不能自动意味着旧运行已执行副作用可以再次运行。修复过程先识别是否派发，再决定接续点。

## 5. 本机直执行优先，企业策略后置

桌面产品默认 **Local Direct**：用户点击运行或在对话要求执行后，直接执行该任务；不逐步弹审批，不按发送/保存/删除等控件名称阻断，不要求用户先编辑应用/路径白名单。

实现顺序上，先让 Local Direct 自动建立 Runtime session 和本机访问上下文，`require_approval=false`，任务所需代码通道启用 trusted-host。已有政策字段仍可供企业使用，但不成为功能完成条件，不扩大审批平台。

此模式必须明确区别于企业受管模式：企业显式配置的管理员策略只在受管模式生效，本机功能不从绕过它来实现。用户本次“先功能”的指令取代旧计划逐项审批的默认 UX。

保留的是执行正确性：停止键、桌面输入单一调度、同 operation 不重复执行、错误目标不点击、执行事实日志。它们防止重复发送、错误文件修改和输入互相打架，不是审批障碍。

macOS 辅助功能/输入监听/屏幕采集、Windows 安全桌面和进程权限等级属于操作系统机制，安装/首次使用引导解决；本项目不能删除这些系统要求。Windows 普通进程无法操作提升权限的目标时应说明原因和提供对应启动入口，不伪报已执行。

## 6. 三层体系的影响

现有代码中对应的是高层 Planner、Jev 局部决策、Runtime/Driver 执行；不是三个独立规划器。`PLAN.md` 原架构和 `planner.py`/`decision.py`/`agent.py` 保留这条旧模型路径；当前 `runtime_workflow.py` 不调用 Planner/Jev。

| 场景 | 高层规划 | 局部决策 | 执行 |
|---|---|---|---|
| 用户人工录制 | 无需调用 | 无需调用 | 捕获事实/控件并生成草稿，不执行录制动作 |
| 正常 Shortcut 回放 | 无需调用 | 唯一定位时无需调用 | 按保存步骤执行/验证 |
| 对话中的新任务 | 已有 Harness/模型拆解目标与选择通道 | 按需定位；Jev 可选，不强制每步使用 | 当前 Runtime 执行 |
| 对话复用 Shortcut | 选择流程、填写参数、组合前后任务 | 正常流程无需调用 | WorkflowRunner 执行 |
| 界面变化修复 | 需要补步骤/改策略时调用 | 候选歧义/视觉目标需要时调用 | 执行已确定的修复步骤并验证 |

所以三层对基础录制和正常回放没有模型依赖影响；它影响聊天调度、流程复用和修复。录制产物可以作为 Harness 的可复用任务，不需要强行把人工事件交给 LLM 再规划一次。

新聊天入口优先复用已经验证接入的 DeepSeek Harness SDK 路径，沿用模型配置和 MCP/SDK 工具。它承担高层 Agent loop；不将旧 Planner/Jev 绑定为唯一任务执行结构。对话与 Shortcuts 的动作共享 Runtime 和同一桌面输入调度。

### 新的真实 app 矩阵

每端五条实际操作链，每条独立录制/复用测试共三次，基础矩阵 30 次：

1. Finder / Explorer：查找、重命名、右键菜单与拖拽移动一份测试文件，文件系统独立核验。
2. TextEdit / Notepad：中文输入/粘贴、键盘选择、快捷键、另存为、关闭后重开；独立核对文件内容。
3. Excel 两端：输入表格/公式、滚动、选择范围、保存、关闭重开；文件读回与应用结果交叉检查。
4. 飞书两端：搜索/打开会话、滚动历史、输入和修改草稿；测试原生树不足时的视觉/输入步骤，草稿值和窗口上下文核验。
5. Safari / Edge：普通网页表单、下拉、滚动、提交和页面结果；区分真实用户浏览器录制与已有隔离 Browser 代码步骤。

第一次在应用原始界面跑，不提前为任务定制控件 label 或加入 app 专属 Core 规则。录制时的手动补步骤、用户指定初始状态等均记录。修复后用同一任务重新测试，原失败保留。

再改变窗口位置/大小、应用重启、100%/150% DPI、第二显示器和输入法；受影响路径分别复跑。对话还需从任务输入到工具动作/结果回读完成；录制/回放不依赖模型服务在线。

UX 测试点击实际 Electron 窗口，不用调用 API 代替界面操作。至少覆盖设置保存/连接测试、会话与任务、录制浮条/停止热键、步骤与画面联动、版本和参数、单步与整段回放、退出重开、sidecar/采集崩溃。自动生成的真实 OS 输入和用户本人演示分别记录。

验收以结果文件/原生读回/目标应用状态评分，不以 UI 显示 completed 评分。还要测视频能播放/定位、长录制内存不持续增长、丢事件/丢帧提示、崩溃后保留已封段；Windows 和 macOS 成绩分别报告。

原完整业务复测保持暂停。以上是一份新建的桌面 UX/录制回放专用 suite。

## 8. 实施顺序

| 阶段 | 可审阅交付物 | 验证 |
|---|---|---|
| D1 桌面宿主与本机执行 | 两端启动包、统一导航、自动 sidecar、设置页、全局停止、Local Direct | 从桌面图标打开；点击真实 app 动作直接执行；退出释放进程/监听 |

| D3 回放覆盖 | native/anchored/visual 输入步骤、右键/组合键/滚动/拖拽、动态定位、结果检查 | Finder/Explorer、Excel、飞书、浏览器任务；不依赖旧坐标/手工后台调用 |
| D4 统一维护与对话 | 分栏编辑、目标选取、视频审阅、参数、版本、重录片段；Harness 流式任务/复用 Shortcut | 从对话引用流程到完成，从维护修改到新版本重放，两条链路同一运行记录 |
| D5 安装与稳定性 | 打包 Python/Swift、双平台分架构构建、签名身份/更新、专用测试报告 | checkout 外安装，真实 app 30 次基础矩阵及变化项、长录制和进程故障测试 |

每阶段是一项交付，不代表一天。首次 2–3 天工程窗口交付 Electron 双平台启动和 TextEdit/Notepad 捕获/回放样本；完整四入口、视频、输入兜底和真实 app 验收按约 4–6 周单人连续工程量安排，D2 实测后按失败项更新。旧 2–4 周估算不再用于扩展后的完整桌面范围。

不先做权限管理平台，也不先重写 Rust Core。Electron 宿主与捕获/输入工具先跑真实应用，录制和维护页随数据链路形成；聊天复用现有 Harness。CrossMacro 只用于交互参考，不拷贝其引擎；Ui.Vision 只参考步骤调试，项目数量不作为交付指标。

## 9. 真正需要控制的三项风险

1. **定位错误或重复执行造成真实数据损失。** 所有输入绑定当前窗口/目标，保留派发事实和唯一操作 ID；有副作用的失败先核查结果。紧急停止和桌面输入串行调度优先做。
2. **录制内容泄露。** 原生密码字段不读明文、敏感画面遮挡/暂停、凭据进系统存储；视频/原始输入不提交 Git，不默认上传模型。不能因为“本地”就声称没有泄露风险。
3. **系统采集/输入和应用行为差异导致链路中断。** 用真实 app 与显示/输入法变化直接验证；事件/视频缺口立即可见，已保存数据可恢复。视觉/输入通道补 UIA/AX 缺口，不能靠稳定 fixture 掩盖。

## 10. 官方机制依据

- [Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer)：屏幕/窗口视频源；系统授权与版本行为按该文档核对。
- [Electron globalShortcut](https://www.electronjs.org/docs/latest/api/global-shortcut)：失焦时停止键，注册失败需处理。
- [Electron BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window)：主窗口/采集窗口/浮条与生命周期。
- [Electron contextBridge](https://www.electronjs.org/docs/latest/api/context-bridge)：界面与桌面宿主之间的具名桥接。
- [Windows Hooks](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-hooks)、[LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)：低层输入回调与超时要求。
- [UIA ElementFromPoint](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation-elementfrompoint)：位置命中原生控件。

技术依据核对日期为 2026-10-14。功能实现仍需按上述阶段交付，本计划的 API 依据与实施验证分别记录。
