## 一、实现改变了什么

`desktop.observe` 新增 `read_nodes`（1–100000）、`read_timeout`（0到30秒之间，含30不含0）、`read_depth`（1–64）及 `view="native"/"web"`。原有 `max_nodes` / `max_bytes` 保持输出限制的含义。

读取结果新增 `read.complete`、停止原因、主遍历/补查访问数、子节点批次数及候选数；部分树的 `total_nodes=null`，并清除可执行动作。Core在审批或派发前拒绝部分树；Jev和Workflow也不能将它当成完整动作依据。预算在遍历/补查边界协作检查，macOS AX还在原生读取前检查；这不是系统调用硬超时。

提前过滤仍需读取顶层窗口身份及全部直接子节点元数据。目标文档正文之外，同应用菜单与独立弹窗保守保留为上下文；**无法证明属于目标窗口的额外菜单/弹窗只读**，不借它们扩大窗口动作权限。操作独立弹窗须显式选择其精确范围并通过原权限检查。目标窗口内的嵌套弹窗保留原行为。

网页视图只整理原生可访问性信息，不截图、不注入DOM、不启动另一种浏览器。保留网页区域的全部后代、表格/嵌套页面层次、原ref、当前值和原状态，同时保留已暴露的弹窗/菜单及祖先路径。多区域无法确定或没有区域时明确失败；输出仍受 `max_nodes/max_bytes` 限制，需要同时检查 `truncated`。

接管使用同一系统用户共享的SQLite状态和原生辅助进程可读的短时状态文件。Windows低级hook和Mac只读CGEventTap只提交必要事件元数据，不记录文字或剪贴板。Windows输入写入 `dwExtraInfo`，Mac输入写入 `eventSourceUserData`；来源不明的注入也按干扰处理。

Core原生动作、前台输入、像素输入、启动/激活、Workflow子动作，以及Jev返回后的派发都有检查点。启用时，不能证明输入来源的旧provider动作会明确拒绝，改用已标记的 `desktop.input` 或已验证原生动作。旧backend CLI和任意宿主脚本不在完全覆盖承诺内。

用户操作后暂停桌面写入。本机继续入口先保持暂停，等待监听器消费当前事件队列并确认按住状态；超时会取消请求，迟到确认不能放行。继续会更新状态版本；旧观察、旧排队请求和旧Jev决策失效，需重新观察。Workflow保存已完成步骤和原回执；确认零派发的暂停请求可以重新观察后提交新请求，未知完成的请求保留原记录，不自动重发。UI的“继续桌面操作”恢复输入许可；已暂停Workflow仍从原运行记录继续，未声称能冻结或自动恢复整个SDK计算线程。

## 二、测到了多少提升

### 合成provider：10个窗口，每个301节点，选取其中一个

两个版本使用同一fixture，各取9次样本中位数。这里的 `children()` 次数是合成provider的方法调用数，**不是Windows UIA或Mac AX系统调用数**。

| 适配器 | 旧版children() | 新版children() | 旧版中位耗时 | 新版中位耗时 |
|---|---:|---:|---:|---:|
| Windows | 3011 | 302 | 28.50ms | 3.12ms |
| macOS | 302 | 302 | 2.77ms | 3.14ms |

Windows该例少了约90%的子节点读取，中位耗时下降约89.0%；目标ref前后相同。macOS原来就有标题过滤，读取次数没有减少，本例新开销反而增加约13.6%。不能据此宣称macOS同样提速，或将Windows合成结果解释成完整任务快90%。

证据：[Windows旧版](evidence/2026-10-18-native-integration/synthetic-windows-before.json)、[新版](evidence/2026-10-18-native-integration/synthetic-windows-after.json)、[Mac旧版](evidence/2026-10-18-native-integration/synthetic-macos-before.json)、[新版](evidence/2026-10-18-native-integration/synthetic-macos-after.json)。

### macOS开发环境：自有原生窗口与Chrome

自有Cocoa窗口完整读取获得80个输出节点；主遍历及AX补查合计166次访问。设置节点预算3后，主遍历访问3个、AX补查0个，并明确返回部分读取。这两个观察的信息量不同，不将其耗时差记作同等任务提速。独立fixture状态文件确认了一次原生文本写入读回。

输入监听现场检查通过：自有标记事件不暂停、无标记的外部模拟CGEvent触发暂停、用户明确继续后恢复。一次模拟输入“发出到状态读回”约13.44ms；**只有一次样本，不是物理输入，也不是接收到事件后的延迟P95**。因此尚不能判定计划中的200ms P95目标达成。

Chrome使用独立临时配置及固定本地页面，并显式启用renderer accessibility。真实Core `desktop.observe(view="web")` 保留9/9项必需信息，包含当前表单值、数量、按钮、交付时间和嵌套页面事实；表格角色由原生树暴露，合成测试另验证行/单元格祖先及原ref不变。Core检查使用 `max_nodes=2000/max_bytes=2000000`，最终 `truncated=false`；不能拿该结果承诺默认输出预算不会截断。

采用**相同浅层节点格式、相同JSON编码**比较，原生输出410节点、312289字节，网页视图385节点、285947字节，减少约8.4%。主要减少浏览器外层信息；菜单上下文仍保留。没有实际模型token/费用数据，没有证明底层读取更快，也没有完整业务成功率数据。

证据：[Mac现场](evidence/2026-10-18-native-integration/macos-live.json)、[Chrome现场](evidence/2026-10-18-native-integration/chrome-macos-live.json)、[固定页面](../fixtures/native-web/index.html)。

## 四、使用方式与限制

Core / MCP / SDK的观察参数示例：

```json
{"app":"目标PID或已授权应用名","window":"实际枚举的精确窗口标题","read_nodes":3000,"read_timeout":5,"read_depth":40,"view":"web","max_nodes":2000,"max_bytes":2000000}
```

不使用网页整理时省略 `view`；不需要新读取预算时省略对应参数。超过预算返回部分读取，不能用增加输出上限来伪装完整树。

接管默认关闭。配置页开启，或运行 `bokkio control enable`；松开按键后通过本机UI或 `bokkio control resume` 继续。`desktop.control`只读状态，不能让模型通过这个工具启用/关闭/恢复；普通读取和非桌面计算可继续。`bokkio control disable`关闭接管。MCP状态读取在AX不可用时仍可用。

仍有明确限制：

1. `Element.children()`整批返回，尚无底层分页；一个巨大的直接子节点批次或阻塞UIA/AX调用不能被Python预算硬中断。
2. 暂停检查与交给操作系统之间仍有时间间隙；已经开始的原生调用及系统队列输入无法撤回。当前检查不能被描述为硬实时保证。
3. 自有按键/鼠标释放做了来源和已派发记录检查；物理用户按住同一键、IME和多设备重叠尚待实测。缺少可靠状态时宁可拒绝继续。
4. Windows hook可能被系统静默移除，Mac tap可能失效；短期心跳和失效暂停能降低风险，不保证识别每次失效。原生辅助程序还依赖短时状态文件传播。
5. 默认支持当前Core/Desktop路径。任意同用户宿主代码可绕开这些检查，这不是宿主代码隔离功能。

后续验收顺序：扩展Windows真实应用矩阵；补Windows Chrome与macOS Edge同一固定页；再跑物理输入/长文本/拖动/IME/修饰键重叠、监听失效与锁屏唤醒；最后构建两端安装包逐项复验。上述缺口完成前，不宣称整份计划验收完成，不默认开启接管，也不宣称业务速度、费用或成功率提高了某个百分比。

首版接管支持范围限定为同一系统用户的单一普通交互桌面；多个RDP登录会话和多用户桌面隔离尚未实现及验收，不扩大支持声明。

本报告此前的“首版”指“本轮功能已实现，尚未完成支持范围验收”，没有指代另一份未公布的功能路线图。接下来先完成以下工作，不另起一批功能开发。

|---|---|---|---|
| 1 | 恢复Windows测试环境，验证Notepad/Explorer多窗口、窗口身份和菜单/弹窗范围 | 不读无关文档正文，目标ref与完整读取一致，范围外零派发 | WinForms双窗口通过，扩展应用待测 |
| 2 | Windows Chrome/Edge及macOS Edge复用固定页，补充切标签、弹窗和导航 | 必需事实/控件及表格关系全部保留；变化后旧观察拒绝写入；缺失信息明确报告 | Mac Chrome与Windows Edge固定页已有结果，其余待测 |
| 3 | 两端物理键鼠、长文字、拖动、IME、修饰键重叠、监听失效、锁屏/唤醒 | 检查点拒绝后续写入；已发出及未知结果保留；恢复不重复执行；分别报告暂停延迟与误暂停 | 只有模拟事件和自动检查，物理场景待测 |
| 4 | 两端安装包逐项复验 | 包内辅助程序、授权主体、监听与任务恢复均可用，不能以开发终端权限代替 | Mac暂存构建通过，安装包待测 |
| 5 | 在相同完整性和任务要求下测耗时、费用、成功率 | 固定输入、版本、预算和独立评分；保留失败、重试与原始数据 | 本轮没有新增完整业务成绩；原业务矩阵仍保持暂停 |

前四项是支持范围验收；第五项用于决定收益和默认配置，须遵守原业务评测的暂停要求。验收中发现的缺陷在原范围内修复。通过验收后也不自动打开所有选项：读取预算、网页视图和接管分别依据结果决定默认值。

以下是条件性研究方向，**当前未安排开发**：若直接子节点整批返回成为主要成本，再评估底层分页；若系统调用阻塞成为主要故障，再评估进程隔离；若出现多RDP会话需求，再设计会话隔离。它们不是本轮待验收功能的隐含后续版本。

## Windows 11 补验与修复

[完整补验记录、原始回归日志及复现命令](evidence/2026-10-18-windows-native/README.md)。当前版本全量读取与指定窗口读取交替各5次：访问数2079对64，中位耗时1672ms对187ms；这是不同读取范围的比较，不能称作旧新版本同范围性能对照，也不能外推为业务提速。Edge原生327节点整理为144个，页面全部38节点的ref和数据保留，包含表格祖先、表单值/勾选和iframe事实。

Windows真实hook识别VM控制台Shift输入并暂停，原生自有标记输入不误暂停；继续后必须新观察，旧操作ID不重发，已派发检查点保留未知结果。Windows聚焦改用目标身份校验后的UIA.SetFocus；两端本机恢复入口等待监听器确认。另修正有效但字段损坏的控制状态、Windows按住状态及跨平台路径测试。物理/IME矩阵未因此完成。

中间曾出现一次异步Workflow状态响应缺少result，原断言没有保留响应错误详情；后续增强错误断言，完整回归及20次独立进程复跑通过，根因未定位，继续列为待观察问题。首次失败、测试脚本断言错误和观察过期均在补验报告保留。
